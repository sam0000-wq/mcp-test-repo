# 團隊程式碼審核規則（AI 審核員的判準）

這份檔案同時被 CodeRabbit（透過 `knowledge_base.code_guidelines`）與人工審查者使用。
修改這份檔案等於修改審核標準，因此納入高風險路徑，需人工核准。

---

## 一、只報這些（必看）

1. 會讓程式在執行時出錯的邏輯問題。
2. 資料遺失、重複寫入、競態條件。
3. 權限繞過、個資外洩、密鑰寫進程式碼。
4. 未處理的例外、空值、逾時。
5. 這次新增的分支沒有對應測試。
6. 對外 API 行為改變但沒有更新文件或版本。

## 二、一律不要報（會直接被忽略）

- 排版、空白、引號、分號、縮排。
- 命名風格（camelCase 還是 snake_case）。
- 「可以考慮重構成…」這類沒有明確錯誤的建議。
- 本次 diff 以外的既有程式碼問題。
- 主觀偏好（箭頭函式 vs function、早返回 vs 嵌套）。
- 引入新套件或升級版本的建議（除非有已知漏洞）。

判斷原則：**說不出「不改會出什麼事」的意見，就不要提。**

## 三、輸出格式

每一條意見必須包含：

- 嚴重度：`[阻斷]` 或 `[建議]`
- 位置：`檔案:行號`
- 問題：一句話講清楚會出什麼錯
- 改法：具體程式碼或明確步驟

`[阻斷]` 只保留給「不修就會壞、會漏資料、會出事」的情況，其餘一律用 `[建議]`。
若沒有 `[阻斷]` 級問題，最後一行寫 `LGTM`。

## 四、高風險路徑的額外檢查

| 路徑 | 額外必查 |
| --- | --- |
| 金流 / 計費 | 金額是否用浮點數、是否冪等、是否有稽核 log、有無回滾 |
| 認證 / 授權 | 有無未授權入口、權限是否只在後端檢查、token 生命週期 |
| 資料庫 migration | 有無 down 腳本、是否鎖表、是否破壞性變更 |
| 基礎設施 / IaC | 權限是否過大、是否把密鑰寫進設定、有無資源上限 |
| 審核管線本身 | 只檢查安全性，不評論結構與風格 |

## 五、明確禁止 AI 做的事

- 不要修改或建議修改整體架構。
- 不要引入新套件。
- 不要提議大規模重寫或「換一套框架」。
- 不要對 `.ai-review/` 與 `.github/` 提出風格意見。

架構決策與底層樣板程式碼屬於人類專屬職權，AI 只能提案，不能定案。

## 六、輪數與升級規則

1. AI 審核最多進行 **3 輪**。
2. 第 2 輪起只檢查本次新增或修改的行，不再全檔重掃。
3. 第 4 輪仍未達成共識，自動標記 `needs-human`，由資深工程師裁決，AI 停止發言。
4. 被標記為「不適用」的意見，記入忽略清單，下次不再提出。

## 七、已知誤報清單（持續累積）

被判定為「不適用」的規則寫在這裡，CodeRabbit 會一併讀取。
每週由一位負責人審一次，避免把真問題也永久消音。

- （範例）`**/*.test.js` 中的 `console.log` 是除錯用途，不需提出。
- （範例）SQL 字串串接在 `src/legacy/` 內是既有技術債，本期不處理。
